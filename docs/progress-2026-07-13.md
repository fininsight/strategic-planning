## 진행상황

### 1. FastAPI 기반 API 구조 정리

- 기존 분석 API가 `app.main:create_app()` 중심의 FastAPI 앱으로 정리됐다.
- API 라우터가 `backend/app/api/routes/` 아래로 분리됐다.
- 현재 라우터는 `health`, `notices`, `analysis`, `checklist`, `files`로 구성되어 있다.
- `scripts/start-analysis-server.sh`가 `uvicorn app.main:app`을 실행하도록 변경됐다.
- CORS 설정은 FastAPI middleware에서 관리하며 `GET`, `PUT`, `POST`, `OPTIONS` 요청을 허용한다.
- README의 백엔드 폴더 구조도 FastAPI 앱, core/db/models/schemas/repositories/api/services 계층을 반영하도록 업데이트됐다.

### 2. SQLAlchemy 모델 도입

- `backend/app/db/`에 SQLAlchemy Base, engine, session 관리 코드가 추가됐다.
- `DATABASE_URL`이 있을 때 SQLAlchemy engine/session을 초기화하고, 없으면 기존 JSON/파일 기반 흐름을 유지할 수 있게 했다.
- `backend/app/models/`에 주요 ORM 모델이 추가됐다.
- 현재 모델은 공고, 첨부파일, 파일 저장본, 문서 추출, 문서 분석, 공고 분석, 크롤링 작업, 체크리스트 상태를 포함한다.
- DB schema 생성은 `Base.metadata.create_all()` 기반으로 초기화된다.

### 3. Repository 계층 도입

- DB 접근 코드가 `backend/app/repositories/` 아래로 분리됐다.
- 공고 저장/조회 로직이 `notice_repository.py`로 이동했다.
- 첨부파일 저장 로직이 `attachment_repository.py`로 이동했다.
- 분석 저장 로직이 `analysis_repository.py`로 이동했다.
- 체크리스트 상태 저장 로직이 `checklist_repository.py`로 정리됐다.
- 작업 상태 저장은 `job_repository.py`로 분리됐다.
- 결과적으로 서비스 계층의 분석/수집 로직과 DB persistence 책임이 더 명확하게 나뉘었다.

### 4. 체크리스트 API 정리

- 체크리스트 상태 API가 FastAPI 라우터로 정리됐다.
- `/api/notices/{bid_no}/{bid_ord}/checklist-state`에서 `GET`, `PUT`, `POST`를 지원한다.
- 요청/응답 스키마가 `backend/app/schemas/checklist.py`로 분리됐다.
- DB 사용 가능 시 `ProposalChecklistState` 모델을 통해 저장하고, DB 미사용 환경에서는 기존 파일 fallback이 유지된다.
- 지난번 구현했던 제출서류 구비 체크 기능이 API 구조 안에 더 안정적으로 편입됐다.

### 5. 분석/저장 파이프라인 확장

- 제안 분석 결과와 문서 분석 결과를 DB에 저장하기 위한 기반이 확장됐다.
- 공고 분석에는 summary payload, proposal sheets payload, combined text storage path, analysis version, status/error가 포함된다.
- 문서 단위 분석에는 attachment별 analysis version, analysis type, analysis payload, status/error가 포함된다.
- 기존 `services/storage/database.py`의 psycopg 기반 best-effort 저장 흐름도 남아 있어, SQLAlchemy 전환 과정에서 호환성을 유지하는 상태다.

### 6. 회사자료 RAG 및 전략수립 기능의 문서화 유지

- 지난번 새로 추가했던 `docs/company-knowledge-rag.md`가 유지되고 있다.
- 회사자료 RAG 운영 원칙은 `.local-data/company-knowledge/sources/`에 내부 자료를 두고, 시장·경쟁 리서치에서 회사자료 근거와 웹 검증 사실을 분리하는 방향이다.
- 전략수립/시장조사 기능은 회사자료 근거를 사용하되, 시장 규모·성장률·수주사실·법령·고시번호는 웹 출처가 있을 때만 검증 항목으로 다루는 원칙을 유지한다.

### 7. AI API 웹검색 리서치 흐름 개선

- 시장·경쟁 리서치가 단일 AI 호출 중심에서 `검색 쿼리 생성 -> web_search 근거 수집 -> 근거 기반 분석 -> 출처 정책 적용` 흐름으로 바뀌었다.
- `market_research_analyzer.py`에서 공고명, 발주기관, 산업/키워드, 제안 분석 결과를 바탕으로 `researchQueries`를 생성한다.
- 검색 쿼리는 `competitors`, `precedents`, `marketTrends`, `companyPositioning`, `factCheck`로 나뉘며, 권위 출처 우선순위(`authorityTiers`)도 함께 구성된다.
- web_search 수집 단계는 경쟁사·컨소시엄, 유사 선행사례, 시장/정책/기술 트렌드, 팩트체크 우선 출처를 그룹별로 검색한다.
- 검색 결과는 URL이 있는 사실만 `webEvidence`로 남긴다. URL 없는 추정 경쟁사, 추정 수주사실, 임의 수치는 근거 항목에서 제외한다.
- 최종 분석 호출은 추가 웹검색을 하지 않고, 이미 수집된 `webEvidence`와 `companyEvidence`만 사용하도록 프롬프트가 바뀌었다.
- OpenAI Responses API 호출은 `LLM_RESPONSES_URL`을 사용하며 기본값은 `https://api.openai.com/v1/responses`다.
- 검색 도구는 `WEB_SEARCH_TOOL` 환경변수로 조정 가능하고, 기본값은 `web_search`다. 400/422 오류가 나면 `tool_choice` 제거 또는 `web_search_preview`로 fallback하는 payload를 순차 시도한다.
- 검색 컨텍스트 크기는 `WEB_SEARCH_CONTEXT_SIZE`로 조정 가능하며 기본값은 `high`다.
- 웹검색 그룹 수는 `WEB_RESEARCH_GROUP_LIMIT`, 그룹별 compact finding 수는 `WEB_EVIDENCE_FINDINGS_PER_GROUP`, 타임아웃은 `WEB_RESEARCH_TIMEOUT`으로 조정한다.
- 최종 모델은 현재 `_research_model()`에서 `gpt-5`로 고정되어 있다.
- 출처 정책이 강화되어 `competitors`, `precedents`, `trends`는 sources가 있는 항목만 남기고, `marketStats`는 `verified`이면서 sources가 있는 항목만 표시한다.
- 출처 없는 외부 사실이 제거되면 warning과 `researchMemory.gaps`에 보강 필요 항목을 남긴다.
- `researchQuality`가 추가되어 검증 출처 수, 검증된 시장 수치, 출처 있는 경쟁사/선행사례/트렌드 수를 계산한다.
- 웹 출처가 부족하면 “시장수치·수주사실은 제안서에 사용하지 말라”는 경고를 반환한다.
- 프론트엔드 타입에는 `webEvidence`, `researchQueries`, `researchMemory`, `researchQuality`가 추가되어 검색 근거와 품질 상태를 받을 수 있게 됐다.
- 전략수립 화면은 검증 출처 수, 미검증 수, source link, fact-check verdict를 기준으로 제안서 사용 가능 여부를 표시한다.

## 현재 상태

- 지난번에는 주요 기능이 로컬 변경사항 위주였지만, 이번에는 해당 작업들이 커밋으로 정리되어 브랜치에 반영된 상태다.
- 최신 브랜치는 FastAPI 라우터, SQLAlchemy 모델, repository 계층을 갖춘 구조로 발전했다.
- README도 새 구조를 설명하도록 업데이트됐다.
- AI API 검색 리서치는 출처 없는 생성 결과를 줄이는 방향으로 크게 개선됐다. 이제 외부 사실은 web_search로 먼저 수집된 URL 기반 근거가 있어야 주요 결과 섹션에 남는다.
- 시장·경쟁 리서치 응답 스키마는 기존보다 커져 `webEvidence`, `researchQueries`, `researchMemory`, `researchQuality`를 포함한다.
- 다만 `services/storage/database.py`의 기존 psycopg 기반 저장 계층과 새 SQLAlchemy repository 계층이 함께 존재한다. 이는 전환기 구조로 보이며, 장기적으로 책임 범위를 정리할 필요가 있다.
- 로컬에서 `git status`와 일부 `git diff` 명령이 응답 없이 멈추는 현상이 있었다. 작업트리 크기, git index 상태, untracked/cache 파일 영향 여부를 별도로 확인해야 한다.

## 남은 할일

### 우선순위 높음

- FastAPI 서버를 실제로 기동해 `/health`, `/api/notices`, `/analysis`, `/proposal-analysis`, `/proposal-mapping`, `/market-research`, `/checklist-state`, `/files` 라우터가 정상 동작하는지 확인한다.
- 프론트엔드에서 기존 API 호출 경로가 FastAPI 라우터와 모두 맞는지 확인한다.
- `DATABASE_URL`이 있는 환경과 없는 환경을 각각 실행해 DB 저장과 파일 fallback이 모두 정상인지 검증한다.
- 체크리스트 저장이 SQLAlchemy repository 경로와 기존 fallback 경로에서 동일한 응답 스키마를 반환하는지 확인한다.
- 공고/첨부파일/분석 저장 로직이 repository 이전 후 기존 분석 캐시와 충돌하지 않는지 실제 공고 1~2건으로 테스트한다.
- `OPENAI_API_KEY` 또는 `LLM_API_KEY`가 있는 환경에서 `/market-research?refresh=1`을 실행해 Responses API 웹검색이 실제로 동작하는지 확인한다.
- `WEB_SEARCH_TOOL=web_search`와 fallback인 `web_search_preview`가 현재 API에서 모두 유효한지 확인한다.
- AI 검색 결과에서 sources 없는 경쟁사/선행사례/시장수치가 실제로 제거되는지 확인한다.
- `researchQuality.sourcedFacts`가 부족할 때 프론트엔드 경고와 백엔드 warning이 자연스럽게 표시되는지 확인한다.
- 멈추는 `git status`/`git diff` 원인을 확인하고, `.DS_Store`, `__pycache__`, 대용량 cache/untracked 파일이 git 성능에 영향을 주는지 점검한다.

### 우선순위 중간

- `services/storage/database.py`와 `repositories/*`의 역할을 정리한다. 단기 호환 계층인지, 장기 유지 계층인지 결정이 필요하다.
- DB schema 생성 방식이 `Base.metadata.create_all()`만으로 충분한지, 운영 전 Alembic 같은 migration 도구를 도입할지 결정한다.
- repository 계층에 대한 최소 단위 테스트를 추가한다.
- FastAPI 라우터별 에러 응답 형식이 프론트엔드에서 처리 가능한 형태로 통일됐는지 확인한다.
- 분석 결과 저장 version 정책과 캐시 무효화 조건을 문서화한다.
- 회사자료 RAG index 생성/재생성 시점과 운영 환경 경로 설정을 README 또는 운영 문서에 더 명확히 반영한다.
- AI API 검색 환경변수(`LLM_RESPONSES_URL`, `WEB_SEARCH_TOOL`, `WEB_SEARCH_CONTEXT_SIZE`, `WEB_RESEARCH_GROUP_LIMIT`, `WEB_EVIDENCE_FINDINGS_PER_GROUP`, `WEB_RESEARCH_TIMEOUT`)를 README나 운영 문서에 추가한다.
- `gpt-5` 고정값을 환경변수로 뺄지 결정한다. 예: `WEB_RESEARCH_MODEL` 또는 `LLM_RESEARCH_MODEL`.
- `webEvidence` 원본을 화면에서 직접 볼 수 있는 디버그/근거 패널이 필요한지 검토한다.
- 캐시 유효성 판단에 `companyEvidence`뿐 아니라 `webEvidence`, `researchQuality`, `researchQueries` 스키마도 포함할지 검토한다.

### 우선순위 낮음

- `backend/app/api/analysis_server.py`의 기존 단일 파일 서버가 계속 필요한지 정리한다.
- 모델/레포지토리/서비스 계층 간 네이밍 규칙을 정리한다.
- API 스키마 문서를 FastAPI OpenAPI 기준으로 검토하고 프론트엔드 타입과 맞춘다.
- `docs/system-architecture.svg`와 README 구조 설명을 최신 repository 계층 기준으로 다시 맞춘다.
- 분석 API 수동 검증 절차를 `docs/`에 체크리스트 형태로 추가한다.
- 권위 출처 tier 판정(`tier1`~`tier4`)을 프론트엔드에서 더 눈에 잘 보이게 표시할지 검토한다.
- 팩트체크 verdict(`VERIFIED`, `PARTIAL`, `OUTDATED`, `WEAK_SOURCE`, `CONTRADICTED`, `NOT_FOUND`)별 필터 기능을 추가할지 검토한다.
